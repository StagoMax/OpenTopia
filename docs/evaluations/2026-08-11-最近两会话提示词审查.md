## 1. 审查口径

这里的“用户轮次”指用户发送一次消息后，到助手最终回复为止；“模型轮次”指这个过程中每次真正向模型发起的请求。一次用户轮次可能因为读取文件、搜索、运行命令、应用补丁等工具调用，被拆成很多模型轮次。

需要区分三层数据：

1. **逻辑上下文**：Harness 组装出的 `contextItems`、历史对话、当前用户消息和工具候选。
2. **供应商传输**：最终发给 `openai_chat_completions` 适配器的 `messages + tools`。
3. **本地 token 估算**：Harness 自己的近似统计。它不等于供应商计费 token，本次审查还发现了图片导致的严重高估。

## 6. 分模块分析与优化建议

### P0：后台完成提醒破坏整个缓存前缀

**现状**：后台命令完成后，Harness 把完整命令与 stdout/stderr 临时加入 `systemPrompt` 的 `opentopia:step_reminder:background_command`。下一轮又移除。虽然 `prompt_cache_key` 没变，但提示词前部字节发生变化，供应商只能命中很短的前缀。

**证据**：第 14、25、37 轮的系统提示分别从 24,469 字符变成 26,710、26,702、28,044；缓存率分别降到 10.1%、8.6%、2.2%，下一轮恢复到约 98%。三轮未缓存输入合计 263,247 token，其中大部分可归因于提醒插入导致历史前缀无法继续复用，但正常新增内容本来也会产生少量未缓存输入。

**优化**：

1. 永远保持稳定系统/开发者前缀字节不变。
2. 后台完成事件追加到对话尾部，作为结构化工具结果或独立的低优先级环境消息，不要插入头部。
3. 首次提醒只发送 `jobId + 状态 + exitCode + 关键摘要 + 截断标记`；完整日志保存在事件/Artifact 中，模型需要时调用 `background_output`。
4. 提醒一旦进入追加式历史，不要下一轮删除；后续由摘要或 checkpoint 正常压缩。

这是最优先修改项，因为它同时降低计费、延迟和长上下文注意力浪费，而且不需要牺牲信息质量。

**实现状态（2026-08-12）**：已完成。`background_command` 不再生成 `opentopia:step_reminder:background_command` developer context，而是生成一组运行时合成的 `runtime_background_completion` Tool Call/Tool Result，追加在当前用户消息和既有工具历史之后。Chat Completions 使用工具消息尾部，Responses 使用 `function_call + function_call_output` 尾部；两种协议都不再改写稳定的 system/developer 前缀。只有模型请求成功到达后才把后台任务标记为已报告，失败时仍会重投。当前仍沿用原有有界日志：stdout 最多 4,000 字符、stderr 最多 2,000 字符；进一步改成 Artifact 引用不在本次范围内。

### P0：图片把本地 token 估算放大约 12 倍

**现状**：`ModelContentPart::Image` 保存 `Vec<u8>`。`token_estimate_breakdown()` 对 `content_parts` 调用通用 JSON 序列化估算，相当于把图片字节当作巨大整数数组计 token。选中请求本地估算 266,911，实际输入只有 21,953，相差 12.16 倍。第一用户轮次也出现 7.4 倍高估。

**风险**：错误触发上下文压缩、预算警告或拒绝请求；仪表盘模块占比失真；优化方向会被误导。

**优化**：为不同内容类型分别估算：

- `Text`：按文本 tokenizer 或当前启发式。
- `Json`：按序列化后的 JSON 文本。
- `Image`：根据供应商协议、图片尺寸和 detail 估算视觉 token；如果无法精确，单列 `imageTokensEstimate` 和图片字节数，绝不序列化 `Vec<u8>` 计文本 token。
- `Resource`：只估 URI/元数据；实际加载后再按真实内容计算。
- 防止 legacy `content` 与 `contentParts` 表示同一内容时重复计数。
- 用 `provider + model + protocol` 的实际 usage 对启发式做滚动校准，但供应商 usage 始终是计费权威。

**实现状态（2026-08-12）**：已完成当前数据结构允许的修复。历史消息和当前用户输入的 `content_parts` 现在按 `Text / Json / Image / Resource` 分型估算，工具结果也从类型化源数据重新估算，不再把图片 `Vec<u8>` 序列化为 JSON 整数数组。图片暂用现有服务端同口径的 `max(bytes / 16, 1,024)` 启发式；由于当前 `ModelContentPart::Image` 没有宽高和 detail，这仍是近似值，供应商 usage 继续作为权威。聚焦测试覆盖了 282,039 字节图片，确保原始 JSON 数组估算至少比新的类型化估算高 8 倍。

### 观察项：本次请求的 eligible 工具全部直发；现有外部工具延迟机制未触发

**现状**：系统已经实现了外部工具渐进披露，并不是任何工具目录都会全量加载。但这个优化主要作用于 Bundled Plugin/MCP 等外部工具：Automatic 模式下，外部工具达到 24 个或外部 Schema 估算达到 12,000 token 才启用客户端 Tool Search；供应商明确支持原生 deferred/tool search 时则可用原生延迟加载。Core 工具仍直接暴露。

这两个会话走自定义 `openai_compatible` Chat Completions 端点。可见工具中有 22 个 Core 工具和 1 个外部 `spreadsheet`，外部目录没有达到 Automatic 阈值，兼容端点也没有被识别为明确支持原生 Tool Search。因此 58 次模型请求都携带 23 个工具，并且每个候选都标记为 `disclosure=direct`；逻辑估算 4,918 token，供应商 JSON 约 19,596 字符。第二个会话实际使用 11 个，第一个只使用 6 个。

**权衡**：首轮和缓存失效轮会重新计算工具 Schema，但稳定工具集合通常可随提示前缀一起缓存。动态拆分 Core 工具会改变工具集合和 cache lineage；自定义 Chat Completions 又需要先调用客户端 `tool_search`、下一模型轮才能使用新加载的 Schema。当前规模下，这个额外轮次和缓存损失可能高于节省的 Schema token。模型曾在没有子代理时调用一次 `wait_agent`，但单个误选不足以证明需要重构 Core 工具面。

**结论**：暂不建议为了这 23 个工具按语义任务动态拆分 Core Schema。保留现有做法：

1. 继续使用模式、权限、Capability Projection 和多代理 `Off` 状态过滤不可能使用的工具。
2. 继续对大型外部工具目录使用原生或客户端 deferred。
3. Core 工具集合在用户轮次内保持顺序和序列化稳定，优先保证缓存。
4. 只有未来 Core 工具数量显著增长，或供应商支持同一响应内原生加载并调用时，再评估 Core deferred。

当前 checkout 也没有发现按本轮附件类型移除 `read_attachment`/`view_attachment` Schema 的路径：现有实现会在附件 manifest 中告诉模型正确工具，由工具执行时校验内容类型，并把图片检查 MCP 后端隐藏在 `view_attachment` 后面；这与“从候选工具目录中移除不适用 Schema”是不同层次的优化。

### P1：历史运行实例中，`shell` Schema 与校验结果发生过矛盾

**现状**：发送给模型的 `shell` Schema 暴露 `yieldTimeMs`，但两次实际调用被执行器以“`arguments.yield_timeMs is not allowed`”拒绝。历史事件中的模型可见契约和执行结果确实矛盾。

当前工作区源码已经使用同一个 `ShellInput` Rust 类型生成模型 Schema和执行反序列化，并且存在带 `yieldTimeMs` 的测试。因此不能仅凭历史事件断定当前源码仍有双源问题；可能是当时运行的桌面二进制、工具注册表和当前源码不在同一版本。

**处理方案**：先用最新构建重启应用，执行一个最小 `shell(command, yieldTimeMs)` 调用复现。如果不再失败，把它归类为旧运行实例问题；如果仍失败，再追踪实际 ToolRegistry。事件中应同时记录应用 build SHA、工具 Schema hash 和执行器 Schema hash，出现不一致时直接报警。契约测试继续覆盖 Schema 中每个可选字段。

### 观察项：结构化选择的 Skill 与模型调用 `read_skill` 是两条不同路径

**现状**：通过消息 `skill_ids` 结构化选择的 Skill 已经在模型调用前加载为 `kind=skill / role=developer / cacheScope=thread`，位置在 volatile world state 和对话历史之前。这条路径设计正确，Skill hash 会进入 cache lineage；本轮第一次使用新 Skill 时会形成新的缓存分支，同一轮后续请求可以稳定复用。

本样本中的 `ui-ux-pro-max` 不是结构化预选，而是模型运行中调用 `read_skill`。它在当前轮作为 Tool Result 追加在消息尾部，不会改写已有缓存前缀；跨用户轮次后则作为“不可信历史工具观察”回放，而不会自动升级为正式 Skill 指令。这符合“工具输出默认不可信”的安全设计，但模型自主选择 Skill 的跨轮语义弱于结构化预选路径。

**结论**：如果产品语义规定只有用户/路由器预选的 Skill 才具有正式指令身份，当前行为可以保留。如果希望模型调用 `read_skill` 也等价于“激活 Skill”，再增加显式的 `activate_skill` 状态转换，而不要把任意 `read_skill` 结果自动提权。

### 观察项：工具历史线性增长，但已有接近上下文上限时的压缩

**现状**：第四个用户轮次有 43 次模型请求、68 组工具调用与结果，最终请求达到 165 个上下文项和 117,916 输入 token。72 次工具调用中有 8 次失败；其中有预期的测试/构建失败，也有正则错误、参数契约错误和无审批删除等可避免失败。

当前同轮压缩会在上下文预算达到约 80% 时启动，压到约 65%，至少保留最近 4 个结果；跨用户轮次也有约 80% 的自动 checkpoint。它的主要目的不是日常省缓存 token，而是避免长任务超过上下文窗口，同时尽量保留精确工具证据。

本样本实现轮缓存率为 89.5%，提前重写历史可能破坏已经建立的缓存并损失细节，因此不建议默认提前压缩。保留以下低风险优化即可：

1. 独立的搜索、读取和检查尽量并行或用 `read_files` 批量完成。
2. 工具调用前由 Harness 做 Schema 级校验和可修复字段提示，避免再消耗一个模型轮次。
3. 在工具结果第一次进入历史前就去除 ANSI 颜色码、重复 Warning 和包管理器样板，避免之后重写已缓存历史。
4. 继续把超长原始输出存为 Artifact，模型上下文只带有界摘要和引用；保留所有未解决错误和最近结果。

### P2：基础契约稳定但偏大，且与动态模块有重复

**现状**：基础契约约 3,432 token，每轮都发送。它可被缓存，所以长会话中的直接计费影响有限，但仍占上下文和首轮成本。它与个性、进度、输出、技能、多代理模块有部分重复；还要求使用“可用计划机制”，而本次实际 23 个工具中并没有计划工具。

**优化**：

- 保留一个短小、永久稳定的核心：身份、指令层级、权限边界、不可信数据、真实性、用户改动保护、完成条件。
- 代码追踪、Git、技能、计划、多代理、文档、视觉和长任务规则按 `experience mode + capability projection + task classifier` 条件加载。
- 如果计划工具没有投影，就不要发送详细的计划证据协议；如果多代理被政策禁用，就不要同时发送整段多代理执行细则和相关工具。
- 用回归评测确认缩短后，越权率、误改率、漏验证率和任务完成率不下降，再逐步上线。

### P2：世界状态可进一步瘦身

选中请求每轮携带约 406 token 世界状态，其中包含 29 个未跟踪文件的完整列表。通常只需发送分支、dirty 状态、修改/未跟踪数量，以及与当前任务相关的路径；完整状态可通过 `git_diff` 或 shell 按需读取。这个优化收益小于缓存提醒和工具 Schema，但实现简单。

## 7. 建议实施顺序

| 顺序 | 改动 | 预期收益 | 质量风险 |
|---:|---|---|---|
| 1 | 后台提醒改为尾部追加式结构化事件 | 本样本三次异常轮合计约 26.3 万未缓存 token，可避免其中的大部分 | 低；只要保留摘要和日志引用 |
| 2 | 修复图片/类型化内容 token 估算 | 预算、压缩、仪表盘恢复可信 | 低 |
| 3 | 统一工具 Schema 与执行器校验 | 减少无效轮次，提高工具成功率 | 低 |
| 4 | 明确结构化预选 Skill 与模型 `read_skill` 的产品语义 | 决定是否需要显式 `activate_skill` | 中 |
| 5 | 保持现有 80% 工具历史压缩阈值，先优化首次进入历史的日志体积 | 避免破坏已有缓存 | 低 |
| 6 | 缩短并条件化基础契约 | 降低首轮成本与注意力噪声 | 中高；必须由评测护航 |

本次按用户确认只实施第 1、2 项。Core 工具动态激活、附件工具投影、Skill 激活语义、工具历史压缩、自定义供应商缓存以及其他建议均未改动。

## 8. 总体判断

这次改造已经把“提示词到底由什么组成”变得明显更可观测：有 `purpose`、模块化 `contextItems`、token breakdown、稳定 cache key 和供应商实际 usage，这一点方向正确。第二个长会话 88.15% 的整体缓存率也说明稳定前缀设计有效。

目前最值得优先修的不是继续删基础提示词或拆分 Core 工具，而是两个确定性问题：**动态后台日志插入指令区导致历史缓存坍塌、图片 token 估算失真**。`yieldTimeMs` 先用最新构建复现；Core 工具和提前压缩则优先保持稳定缓存，不作为当前优化项。
