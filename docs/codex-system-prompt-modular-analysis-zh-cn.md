# Codex 系统提示词模块化拆解：固定底座、动态装配与设计原理

## 1. 分析范围与核心结论

本文分析对象是 [`codex-rollout-prompts-zh-cn.md`](./codex-rollout-prompts-zh-cn.md)。原文来自两份 Codex Desktop rollout 日志，包含 `base_instructions`、多组 `developer` 消息、环境上下文、逐轮元数据，以及上下文压缩后的重新注入记录。

最重要的结论是：Codex 实际使用的指令不是一份静态的“超级系统提示词”，而是一套分层装配的运行时策略。它至少由以下几类信息共同构成：

1. 产品级行为底座：规定 Agent 身份、工作方式、沟通方式、授权边界和通用操作纪律。
2. 条件性能力模块：根据 Codex 运行界面、协作模式、插件、Skills、多 Agent 开关等条件选择性加入。
3. 用户设置与会话配置：个性、模型、推理强度、权限、审批、沙箱、多 Agent 策略等。
4. 每轮运行态：工作目录、日期、时区、工作区根目录、可用工具、并发槽位和当前 turn ID 等。
5. 会话历史：用户请求、工具结果、中间进度、压缩摘要和恢复后的历史替代内容。

因此，“固定”和“动态”不能只做简单二分。更准确的划分是：

| 类别 | 含义 | 例子 |
|---|---|---|
| 固定底座 | 在同一产品版本和提示词版本内，不由普通用户设置改变 | 授权边界、修改文件的基本纪律、工具调用前的进度说明、Skill 的加载协议 |
| 条件固定模板 | 模板本身固定，但只在某种产品形态或配置成立时加入 | Desktop 的媒体渲染规则、Default 模式规则、多 Agent 团队协议 |
| 动态实例值 | 文本或结构由用户设置、安装状态、会话状态或当前轮次生成 | `cwd`、日期、Skill 列表、缓存版本路径、审批策略、并发槽位 |

> “全部用户都一样”只能理解为“在同一 Codex 产品版本、同一运行界面和同一功能条件下，不由用户配置个性化的规则”。两份 rollout 样本不足以证明某段文字在所有版本、所有客户端、所有账号和所有模型上永久相同。

## 2. 整体装配模型

可以把第 `t` 轮的有效上下文抽象为：

```text
EffectiveContext(t) =
    BaseInstructions(personality, productVersion)
  + PermissionPolicy(sandbox, approval, network)
  + AppContext(surface, appCapabilities)
  + CollaborationMode(mode, availableTools)
  + PluginProtocol(pluginSystemEnabled)
  + SkillCatalog(installedSkills, enabledPlugins, cacheVersions, turn)
  + MultiAgentProtocol(protocolVersion, role, concurrency)
  + MultiAgentPolicy(activationMode)
  + Environment(cwd, shell, date, timezone, workspaceRoots)
  + TurnContext(model, effort, featureFlags, ids)
  + ConversationHistoryOrCompaction(t)
  + UserMessage(t)
```

工具定义更适合视为与文字提示词并列的一条输入，而不是普通自然语言的一部分：

```text
AvailableActions(t) = ToolSchemas(surface, plugins, mode, permissions, runtime)
```

模型最终能做什么，由两者的交集决定：

```text
可执行行为 = 指令允许的行为 ∩ 本轮真实存在的工具能力 ∩ 当前权限允许的范围
```

这解释了原文中的一个关键规则：即使文字提到了 `request_user_input`，只有本轮工具清单真的列出它时才能调用。反过来，一个工具即使存在，也不代表可以无条件使用；授权边界、多 Agent 启动策略和用户请求范围仍然限制其使用。

## 3. 哪些内容固定，哪些内容按需拼装

### 3.1 判定总表

| 模块 | 固定性 | 是否对所有用户相同 | 主要装配条件或变量 | 证据强度 |
|---|---|---|---|---|
| Agent 身份与目标 | 固定底座 | 同版本大概率相同 | 产品和模型代际可能改写 | 高 |
| 个性描述 | 按设置选择模板 | 否 | `personality: friendly` 等个性设置 | 中高 |
| 写作与技术沟通 | 固定底座与个性模板混合 | 不宜笼统视为相同 | 产品版本、个性配置 | 中 |
| `commentary` / `final` 协议 | 固定底座 | 同一交互协议下相同 | 客户端是否支持对应频道 | 高 |
| 文件编辑、自主性、授权边界 | 固定底座 | 同版本大概率相同 | 产品策略版本 | 高 |
| Skill 通用加载规则 | 条件固定模板 | 启用 Skills 的用户相同 | Skill 系统是否启用 | 高 |
| 权限说明 | 动态模板 | 否 | sandbox、approval、network | 高 |
| Desktop 应用规则 | 条件固定模板 | 仅 Desktop 同版本用户相同 | `surface = desktop`、App 功能集 | 高 |
| 协作模式规则 | 按模式选择模板 | 否 | Default 或 Plan | 高 |
| 插件通用协议 | 条件固定模板 | 启用插件系统时相同 | 插件系统是否可用 | 高 |
| 本轮 Skill 目录 | 动态实例 | 否 | 安装、启用、插件版本、缓存路径 | 高 |
| 多 Agent 团队协议 | 条件固定模板加动态值 | 否 | 协议版本、主从角色、并发槽位 | 高 |
| 多 Agent 启动策略 | 按设置选择模板 | 否 | `explicitRequestOnly` 等策略 | 高 |
| 环境上下文 | 完全动态 | 否 | cwd、shell、日期、时区、根目录、权限 | 高 |
| `turn_context` | 完全动态 | 否 | turn ID、模型、effort、flags、模式 | 高 |
| 工具 schema | 完全动态 | 否 | 客户端、插件、MCP、权限、本轮能力 | 高，但原文未展开 schema |
| 对话历史与压缩摘要 | 完全动态 | 否 | 历史、上下文长度、压缩时点 | 高 |

### 3.2 可以归入“全部用户共用底座”的内容

在限定为“相同提示词版本的 Codex Agent”后，以下规则没有显示出由用户设置驱动的迹象：

- Agent 的总目标是与用户在共享工作区内协作，直到目标真正完成。
- 先理解现有代码和工作区状态，再进行范围内修改；不破坏用户已有改动。
- 根据请求类型区分只读回答、诊断、实现、监控，不把一种授权擅自扩大成另一种授权。
- 工具调用要可解释、可跟踪、尽量并行；长任务需要持续提供简短进度。
- 最终答案聚焦结果，并准确说明验证情况和未完成事项。
- 使用 Skills 时遵循触发、完整读取、最小集合、渐进披露、复用资源和失败回退规则。
- 结构化能力必须通过真实工具或规定的结构化指令使用，不能仅凭文字假装调用成功。

这里的“共用”指规则语义，而不保证逐字文本跨版本不变。例如 `rg`、`apply_patch` 等具体工具偏好是当前版本的工程策略，将来可以升级。

### 3.3 明确属于按需拼装的内容

以下内容会根据用户设置、产品形态或运行状态改变：

- 个性：原文的 `base_instructions` 使用友好、富有主体性的沟通风格，同时 `turn_context.personality` 为 `friendly`，两者存在明显对应关系。因此个性段落很可能是按 personality 配置选择或生成，而非所有用户统一。
- 运行界面：`<app-context>` 明确声明 Codex Desktop。CLI、网页端或其他宿主不会无条件需要 Desktop 的图片渲染、线程指令和 UI directive。
- 权限：`danger-full-access`、`approval_policy: never`、网络开关和文件系统 profile 都是当前会话值。
- 协作模式：Default 和 Plan 有不同 developer 指令，且只能由新的 developer 层模式注入切换。
- 插件和 Skills：目录由当前安装、启用状态和本地缓存版本生成，运行中还能单独刷新。
- 多 Agent：协议是否存在、启动策略、角色路径、并发槽位和可选模型都可能变化。
- 环境与逐轮状态：目录、日期、时区、工作区根目录、turn ID、模型和推理强度都是实例值。
- 工具清单：工具是否存在由本轮 runtime 暴露的 schema 决定。
- 压缩内容：取决于会话历史和上下文预算，每个任务都不同。

## 4. 用户设置到提示词模块的映射

| 用户设置或运行配置 | 影响的模块 | 具体影响 |
|---|---|---|
| Personality | `base_instructions` | 个性、语气、沟通偏好；可能连带调整写作风格 |
| Model | `turn_context`、身份文本、子 Agent 继承规则 | 当前模型标识，以及派生 Agent 是否允许覆盖模型 |
| Reasoning effort | `turn_context`、子 Agent 继承规则 | 当前推理强度和完整历史派生时的继承行为 |
| Collaboration mode | `<collaboration_mode>` | Default 或 Plan 的行动和提问方式 |
| Sandbox / permissions | `<permissions instructions>`、`environment_context`、`turn_context` | 可读写范围、是否需要审批、调用命令时使用什么参数 |
| Network access | 权限模块、实际工具能力 | 是否能执行联网操作；文字允许仍需实际 capability 支持 |
| Installed plugins | `<plugins_instructions>`、Skill 目录、工具 schema | 新增带命名空间的 Skills、MCP 工具和应用工具 |
| Installed personal Skills | `<skills_instructions>` | Skill 名称、触发描述、`SKILL.md` 路径 |
| Multi-agent mode | 团队协议和覆盖策略 | 是否允许主动委派，或仅在用户、`AGENTS.md`、Skill 明确要求时启动 |
| Surface / app | `<app-context>`、工具 schema | Desktop、CLI 或其他宿主所支持的渲染和交互能力 |
| Workspace selection | `environment_context` | cwd、workspace roots、visualizations 目录 |
| Summary strategy | `turn_context` 和压缩流程 | 是否自动压缩，以及恢复轮怎样重建历史 |
| Realtime flag | `turn_context` | 是否启用实时模式；原文没有给出其进一步行为规则 |

## 5. 模块一：`base_instructions`

### 5.1 身份与任务契约

核心规则：

- Codex 是能使用工作区和工具执行任务的 Agent，不只是问答模型。
- 完成标准是用户目标“真正得到处理”，而不是仅给出建议或半成品。
- 与用户共享工作区意味着必须尊重现有文件、未提交修改和用户资产。

蕴含原理：

- **结果导向**：衡量标准从“回复是否合理”提升为“任务是否闭环”。
- **环境落地**：答案和工作区实际状态必须一致，避免只在文本中声称完成。
- **共同所有权边界**：共享不等于随意支配，用户已有改动默认属于用户。

固定性判断：任务契约属于产品级固定底座；“基于 GPT-5”等模型代际描述可能随产品版本变化。

### 5.2 个性、写作与技术沟通

核心规则：

- 匹配用户语气和理解程度，保持有主体感但不过度表演。
- 先讲结果，再讲过程；优先使用朴素语言。
- 格式服务于理解，不机械堆叠标题、粗体、列表和图示。
- 对异议使用证据和推理，而不是无依据地迎合。

蕴含原理：

- **认知负担控制**：通过结果优先和最少格式降低二次阅读成本。
- **自适应沟通**：同一技术事实根据用户背景改变解释密度。
- **可信协作**：独立判断和证据比表面顺从更能建立可靠性。
- **界面感知**：Markdown 空行、绝对路径和渲染约束不是审美细节，而是输出协议。

固定性判断：写作的基本原则可能是固定底座，但原文的“老朋友”“主体性”等表述与 `personality: friendly` 高度吻合，应视为个性模板的一部分，不能认定所有用户都相同。

### 5.3 `commentary` 与 `final` 双频道

核心规则：

- 工具调用前先在 `commentary` 说明当前工作。
- 持续工作时定期更新，原文阈值是不超过 60 秒没有进度。
- `commentary` 只承载阶段性信息；阻塞性的最终问题放在 `final`。
- `final` 必须自包含，因为中间进度会在 UI 中折叠。
- 用户中途追加或覆盖请求时，按最新意图调整当前任务。

蕴含原理：

- **可中断执行**：长任务不是黑箱，用户可以根据实时状态纠偏。
- **事件流与交付物分离**：进度日志和最终成果使用不同频道，避免最终答案依赖隐藏历史。
- **并发输入处理**：用户在 Agent 工作期间仍可发消息，提示词定义了抢占、追加和状态询问的处理策略。

固定性判断：这是支持相应频道的客户端交互协议，属于条件固定模板。没有相同频道能力的宿主可能使用不同协议。

### 5.4 工程操作纪律

核心规则：

- 文本和文件搜索优先使用 `rg` / `rg --files`。
- 独立的工具调用尽量并行。
- 文件修改使用 `apply_patch`，避免不必要的脚本化写入。
- 不执行未经明确授权的破坏性 Git 命令。
- 不覆盖不属于当前任务的工作树修改。
- 避免长时间阻塞等待，以保持对用户可见。

蕴含原理：

- **确定性和可审计性**：补丁比隐式重写更容易核验改动边界。
- **低延迟**：并行读取和搜索减少工具往返时间。
- **可恢复性优先**：保留用户修改，减少不可逆操作。
- **输出卫生**：命令不仅要正确，还要避免噪声和敏感信息泄露。

固定性判断：属于当前 Codex 工程 Agent 的固定操作策略，但具体工具偏好会随运行环境和版本变化。

### 5.5 请求类型与授权状态机

原文实际上定义了一个轻量状态机：

| 用户请求类型 | 默认允许的动作 | 默认不授权的动作 |
|---|---|---|
| 回答、解释、评审、报告状态 | 只读检查、证据收集、回答 | 外部写入、改代码、发消息、修改 PR |
| 诊断 | 定位原因并解释，可做非破坏性验证 | 自动实施修复 |
| 修改或构建 | 实现、验证、交付 | 超出范围的扩张和外部副作用 |
| 监控或等待 | 使用产品提供的等待或监控机制 | 因“无变化”提前判为失败 |

附加约束：

- “完成”“不要停止”会增强持续性，但不会扩大授权范围。
- 可以做低风险、范围内的合理假设。
- 需要新权限、外部协调或会实质改变结果的用户选择时，必须停下并请求方向。

蕴含原理：

- **最小授权**：从用户的动词推导允许的副作用等级。
- **意图和能力分离**：技术上能执行，不等于用户已经授权。
- **风险分级自治**：低风险且可逆的步骤主动执行，高影响决策交还用户。

这是最接近“所有用户一致”的策略底座之一，因为它不依赖当前目录、插件或个性设置。

## 6. 模块二：工具调用系统

### 6.1 原文包含什么，不包含什么

原文包含大量工具使用规则和工具名称，但没有完整展开本轮所有工具的 JSON schema。因此需要区分：

- **工具政策**：何时可以调用、调用前后如何沟通、优先选哪个工具、失败如何回退。这部分在提示词中。
- **工具能力**：工具名、参数、返回值和是否真实可用。这部分通常由 runtime 以 schema 动态提供。
- **工具权限**：即使 schema 存在，权限、审批策略和用户授权仍可能禁止某类调用。

不能从原文推断网络 API 的完整请求体，也不能把日志中出现过的工具名视为任何一轮都必然存在。

### 6.2 工具调用流程

```text
识别用户意图
  -> 判断请求类型和副作用授权
  -> 检查是否触发 Skill 或专用能力
  -> 确认本轮工具真实存在
  -> 在 commentary 说明当前动作
  -> 调用工具，独立调用可并行
  -> 读取结果并处理错误或回退
  -> 按风险执行验证
  -> 在 final 报告真实结果
```

这一流程包含几个重要原则：

1. **Capability discovery**：先确认本轮能力，避免幻觉式工具调用。
2. **专用能力优先**：自动化、线程、文档依赖等任务优先使用专用工具或 schema，而不是手写协议。
3. **策略与执行分离**：自然语言决定是否应该做，tool schema 决定怎样合法地做。
4. **成功后发事件**：Git 和线程的 `::...` UI directive 只有在真实操作成功后才输出，防止 UI 状态与实际状态分叉。
5. **验证与风险成比例**：小改动做聚焦验证，共享行为或高影响工作扩大验证范围。

### 6.3 直接工具与 shell 编排的边界

多 Agent 模块明确规定，协作工具不能从 `functions.exec` 内部间接调用，必须以直接工具调用方式使用。这体现了能力边界：

- shell 适合文件、构建、测试等工作区操作。
- 应用级或编排级工具保留独立调用通道，以便权限、消息路由和审计保持清晰。
- 某个工具不在 `tools.*` 命名空间中，不应通过字符串或 shell 模拟它。

这类规则的模板通常固定，但实际有哪些工具、工具属于哪个命名空间是动态的。

## 7. 模块三：权限与安全边界

### 7.1 权限模块的组成

原文示例值为：

- `sandbox_mode = danger-full-access`
- `approval_policy = never`
- 网络已启用
- `permission_profile.type = disabled`
- 文件系统访问为 `unrestricted`

这些都是当前会话实例值，不是所有用户的默认值。提示词会根据实际权限生成对应说明，例如某些配置下可能要求在调用工具时携带审批参数，而当前样本明确禁止提供 `sandbox_permissions`。

### 7.2 权限设计原理

- **显式能力边界**：模型不需要猜测文件系统或网络是否可用。
- **配置驱动命令形态**：同一个命令在不同审批策略下可能需要不同参数。
- **纵深约束**：文件系统 sandbox、tool schema、developer 规则和用户授权共同限制行为，而不是依赖单一防线。
- **权限不等于授权**：`danger-full-access` 只说明技术权限广，不代表用户允许任意修改或删除。

权限模块是“固定模板 + 动态值”的典型：说明权限的机制固定，具体权限完全动态。

## 8. 模块四：Codex Desktop 应用协议

`<app-context>` 不是通用推理规则，而是宿主应用适配层。

### 8.1 媒体、文件与渲染

- 本地图片和视频使用绝对路径的 Markdown 图片语法。
- 本地代码和工作区文件使用绝对可点击路径。
- 复杂关系可用 Mermaid，并遵循节点标签转义规则。
- Web URL 返回为 Markdown 链接。

原理是让模型输出能被 Desktop UI 正确解析，而不是只在人类阅读层面“看起来像链接”。

### 8.2 文档运行时

表格、幻灯片和文档任务先加载工作区捆绑依赖。其原理是避免假设系统 Python、Node 或库版本，使用宿主已验证的运行时保证可重复性。

### 8.3 自动化和线程

- 自动化使用 `automation_update` 一类专用 schema。
- 线程管理优先使用 thread tools。
- `create_thread` 只用于用户明确要求的新任务；当前请求的内部子任务和用户拥有的新线程不是同一概念。
- 异步线程创建后要显式等待或返回 UI directive。

原理是区分两种并行模型：

| 模型 | 所有权 | 用户可见性 | 用途 |
|---|---|---|---|
| Codex task / thread | 用户拥有 | 出现在侧边栏 | 独立、可持续跟进的任务 |
| 内部 sub-agent | 当前主 Agent 管理 | 通常不作为独立用户任务 | 当前请求内部的并行子工作 |

### 8.4 UI directives

`::code-comment{...}`、`::git-stage{...}`、`::git-commit{...}`、`::created-thread{...}` 等不是普通说明文字，而是 Desktop UI 可解析的事件协议。其共同规则是：

- schema 必须准确；
- 只在对应动作成功后输出；
- 通常单独占一行；
- 没有可执行结果时不输出；
- commentary 不承载最终状态 directive。

这一模块只对支持这些协议的宿主成立，因此属于条件固定模板。

## 9. 模块五：协作模式

原文处于 Default 模式，核心策略是优先作出合理假设并执行，只有无法从本地上下文查明且猜测风险较高时才提问。

关键规则：

- 模式只由新的 developer 指令切换；用户说“进入 Plan 模式”本身不会改变底层 collaboration mode。
- `request_user_input` 只有在本轮工具列表中存在时才能使用。
- Default 模式需要提问时，用简短纯文本；不能把工具专用的多项选择格式伪装成普通消息。

蕴含原理：

- **模式是控制平面状态**：它由上层编排器管理，不由普通对话文本自行改写。
- **减少不必要阻塞**：Default 偏执行，Plan 则可能有不同的用户决策协议。
- **界面能力一致性**：没有结构化提问工具时，不能假装 UI 会渲染选项。

该模块明确按设置拼装，不能归入所有用户固定内容。

## 10. 模块六：Plugins 与 Skills

### 10.1 Plugin 是能力容器，Skill 是路由与工作流

原文把 Plugin 定义为 Skills、MCP servers 和 apps 的本地包，但 Plugin 本身不被直接“调用”。模型实际使用的是：

- Skill：任务触发条件、流程、参考资料和资产复用规则；
- MCP tool：结构化外部能力；
- app tool：宿主或连接应用能力。

带 `plugin_name:` 前缀的 Skill 用命名空间标记来源，MCP 工具则通过工具 provenance 识别来源。

### 10.2 Skill 的渐进披露流程

原文定义了三层加载：

```text
第 1 层：本轮 Skill 目录
  只有名称、描述、来源位置，用于判断是否触发

第 2 层：选中 Skill 的 SKILL.md
  一旦触发必须完整读取，不能只读一部分

第 3 层：Skill 直接引用的 references / scripts / assets
  只加载当前任务必需的资源
```

规则包括：

- 用户点名或任务明显匹配时，本轮必须使用。
- 多个 Skill 适用时选择能覆盖任务的最小集合，并说明顺序。
- 选中后主 Agent 必须亲自完整读取 `SKILL.md`。
- 仅按路由读取必要参考，不做无目的深层追踪。
- 优先复用 Skill 的脚本、模板和资产。
- 无法使用时说明问题并回退。
- Skill 不跨轮自动继承，除非用户再次提及或新一轮重新触发。
- 用户指令优先于 Skill 的一般准则。

### 10.3 为什么 Skill 目录是动态的

原文记录了多次仅重新注入 `<skills_instructions>` 的情况，且差异包括：

- `openai-docs` 的触发描述版本变化；
- Chrome、computer-use 等插件缓存版本路径变化；
- Skill 列表来自当时本机和插件缓存，而非写死在 `base_instructions`。

这证明了 Skill 系统采用“稳定加载协议 + 动态能力目录”的设计。优点是无需重写整个基础提示词即可热更新能力；代价是同一会话不同轮次的可用 Skill 和版本可能不同，模型必须以本轮目录为准。

### 10.4 Skill 设计原理

- **上下文节省**：先看短目录，命中后才加载完整流程。
- **确定性路由**：名称和触发描述把自然语言请求映射到专门工作流。
- **能力可扩展**：新增插件或 Skill 不需要修改 Agent 的所有核心指令。
- **来源可追踪**：路径、命名空间和 provider 明确能力来自哪里。
- **主 Agent 负责解释**：不允许把 Skill 指令的阅读和解释委派出去，避免控制逻辑在多 Agent 间失真。

## 11. 模块七：多 Agent 系统

### 11.1 能力层和策略层必须分开看

原文先注入多 Agent 团队协议，说明主 Agent 可以生成子 Agent；随后又注入覆盖规则，禁止主动委派，除非用户、适用的 `AGENTS.md` 或 Skill 明确要求。

这不是矛盾，而是两层控制：

| 层 | 回答的问题 | 原文内容 |
|---|---|---|
| 能力层 | 系统会不会、多 Agent 怎样工作 | root 角色、spawn、消息、共享目录、并发槽位、上下文继承 |
| 策略层 | 当前任务什么时候允许启动 | `explicitRequestOnly`，没有明确触发时不得生成子 Agent |

也就是说：**具备能力不等于当前被授权使用能力**。

### 11.2 团队拓扑

- `/root` 是主 Agent，负责任务整体闭环。
- 子 Agent 可以继续生成子 Agent，形成层级任务树。
- `spawn_agent` 创建子任务；`followup_task` 让空闲 Agent 开始新一轮；`send_message` 只传消息，不自动触发新一轮。
- 消息通过 analysis 频道按 recipient、author、payload 结构路由。
- 所有 Agent 共享容器、文件系统和当前目录，文件修改立即可见。
- 并发槽位限制同时活动的 Agent 数量。原文样本为 4，这个数字应视为运行时配置而非固定常量。

### 11.3 上下文派生

`fork_turns` 控制子 Agent 获得多少父上下文：

- `all` 或省略：继承完整历史，同时继承父模型和推理强度，不接受覆盖。
- `none` 或正整数：只给无上下文或最近若干轮，可在明确授权条件下指定模型或 reasoning effort。

其核心权衡是：

| 选择 | 优点 | 代价 |
|---|---|---|
| 完整历史 | 语境最完整，交接成本低 | token 成本高，可能携带无关信息 |
| 部分历史 | 上下文更聚焦，成本更低 | 必须在任务描述中补全约束和背景 |
| 无历史 | 隔离最强，适合独立探索 | 最容易因缺少背景产生偏差 |

### 11.4 共享文件系统的含义

共享文件系统让并行 Agent 不需要手工传输产物，但会带来一致性风险：

- 两个 Agent 同时修改同一文件可能互相覆盖或产生难以归属的差异。
- 主 Agent 必须把子任务划分到独立、边界清楚的文件或只读分析。
- 子 Agent 的文件变化会立即影响主 Agent 后续读取，因此验证必须基于最新工作树。
- 工作树中的未知改动仍默认属于用户，不能因为多 Agent 存在就放宽保护规则。

### 11.5 多 Agent 的设计原理

- **受控并行**：并发用于独立且有价值的子任务，不是默认把所有工作拆散。
- **上下文可配置复制**：根据任务耦合度控制信息传递成本。
- **主 Agent 单点交付**：子 Agent 提供结果，主 Agent 负责合并、验证和面向用户交付。
- **策略覆盖能力**：最晚、最具体的 developer 策略可以收紧前面授予的能力。
- **显式触发降低浪费**：`explicitRequestOnly` 避免简单任务因自动并行增加成本、延迟和写冲突。

## 12. 模块八：环境与逐轮上下文

### 12.1 `environment_context`

环境消息提供模型不能可靠从语言历史中推断的事实：

- 当前工作目录；
- shell；
- 当前日期和时区；
- 工作区根目录；
- visualizations 输出目录；
- 权限 profile 和文件系统访问类型。

原文显示这些字段会在后续轮次变化，例如日期推进、visualizations 根目录更新、工作区新增 `J:\Project\RAG`。因此它是纯动态注入。

设计原理：

- **事实新鲜度**：时间、目录和权限以当前 runtime 为准，不依赖旧对话记忆。
- **范围锚定**：workspace roots 告诉 Agent 哪些路径属于用户置于范围内的系统。
- **平台适配**：shell 决定命令语法，时区决定“今天”等词的解释。

### 12.2 `turn_context`

`turn_context` 是逐轮元数据，包含：

- 唯一 `turn_id`；
- cwd、workspace roots、日期、时区；
- approval、sandbox、permission profile；
- model、reasoning effort、personality；
- collaboration mode；
- multi-agent 协议和启动模式；
- realtime、summary 等 feature flags。

这里需要谨慎：rollout 记录表明这些元数据存在，但不能仅凭日志断言每个字段都以相同方式进入所有网络请求或都被模型逐字看到。原文也明确提醒，日志记录顺序不等于完整 API 请求体。

### 12.3 环境消息与 `turn_context` 为什么有重复字段

两者重复 cwd、日期、权限等信息，可能服务于不同层次：

- 环境消息面向 Agent，提供可直接使用的自然语言/XML 上下文。
- `turn_context` 面向运行时记录和编排，保存机器可读状态。

这是基于结构的合理推断，不是原文明确公布的内部实现契约。

## 13. 模块九：上下文工程与压缩恢复

### 13.1 首轮和后续轮并不重复注入所有内容

原文记录的典型顺序是：

```text
首轮：
base_instructions
  -> Desktop developer 消息
  -> 多 Agent 团队消息
  -> 多 Agent 覆盖消息
  -> environment_context
  -> turn_context
  -> 用户输入

普通后续轮：
turn_context
  -> 用户输入

能力刷新轮：
新的 skills_instructions
  -> 其他逐轮内容

压缩恢复轮：
重放必要 developer 模块
  -> 重新注入环境
  -> 新 turn_context
  -> 压缩后的历史
  -> 用户输入
```

这说明 rollout 是事件式记录，不是每轮把整套固定文本重新抄一遍。会话建立时加载稳定规则，后续只记录增量；发生压缩或恢复时再重建必要控制上下文。

### 13.2 压缩的连续性规则

`base_instructions` 要求：

- 看到摘要时假定发生了 compaction；
- 不从头重做；
- 不重复已经发出的 commentary；
- 对摘要缺失部分作范围内合理假设；
- 把跨压缩的同一轮看作连续工作链。

其原理是让长任务突破模型单次上下文窗口，同时保持用户感知上的连续性。

### 13.3 压缩内容的可见性边界

样本中的 `type: "compaction"` 正文只有 `encrypted_content`，没有可翻译的明文。因此可以确认“存在加密摘要对象”，但不能从该文档还原摘要算法、摘要内容或选择策略。

### 13.4 上下文工程的总体原则

- **稳定规则常驻或可重放**：核心 developer 模块在恢复时重新纳入。
- **动态状态增量刷新**：日期、目录、Skill 目录和 turn ID 独立更新。
- **能力渐进披露**：Skill 先目录后正文，再到必要资源。
- **历史有损压缩，任务状态保持连续**：减少 token，同时避免重启任务。
- **控制上下文和业务上下文分层**：模式、权限、工具是控制面；用户请求和文件内容是任务面。

## 14. 指令优先级与覆盖关系

原文没有给出一份完整、正式的优先级规范，但能观察到以下明确关系：

1. 新的 `<collaboration_mode>` developer 指令可以使此前模式指令失效。
2. 多 Agent 覆盖 developer 消息可以收紧前一条团队能力消息。
3. 用户指令优先于 Skill 中的一般准则。
4. 用户请求不能自行改变 developer 层 collaboration mode。
5. 工具描述不能自行改变 collaboration mode。

由此可以归纳出一个实用模型：

```text
平台和 developer 控制策略
  > 用户对当前任务的目标与范围
  > Skill 提供的领域工作流默认值
  > Agent 自己选择的实现细节
```

同一层中，后注入且更具体的限制可以收紧前面的宽泛能力。例如“可以生成子 Agent”描述能力，而后续“仅明确请求时可生成”规定当前激活条件。

这部分是从样本行为归纳的解释模型，不应冒充 OpenAI 对外发布的完整指令优先级规范。

## 15. 这套提示词体现的系统设计原则

### 15.1 提示词是策略编译器，不是静态文案

用户设置、应用形态、能力清单和运行态被编译成多段指令。固定的是装配规则和模块模板，变化的是被选中的模块及其实例值。

### 15.2 能力、策略、权限三分

- 能力：有没有 tool schema，系统会不会做。
- 策略：当前场景应不应该做。
- 权限：runtime 是否允许做，以及是否需要审批。

这三者取交集，能避免“工具存在即滥用”或“提示词允许但执行环境不支持”。

### 15.3 以副作用为中心的自治

Agent 对只读、可逆、范围内操作更主动；对外部写入、不可逆操作和实质性选择更谨慎。这比简单的“总是询问”或“总是自动执行”更适合工程任务。

### 15.4 渐进披露控制上下文成本

Skill 目录、完整 `SKILL.md`、必要 references 构成三级加载。多 Agent 的 `fork_turns` 和历史 compaction 也是同一个思想：只把完成当前决策真正需要的信息送入上下文。

### 15.5 UI 输出也是协议

绝对路径、Markdown 媒体、Mermaid、`::git-*` 和 `::code-comment` 都说明最终文本不仅给人阅读，也被客户端解析。提示词同时承担自然语言协作协议和机器界面协议。

### 15.6 长任务按事件流设计

commentary 更新、用户中途消息、异步线程等待、Agent 消息和 compaction 恢复共同构成可中断、可恢复的事件流，而不是“一问一答”的单次生成。

### 15.7 多 Agent 是受策略约束的执行资源

多 Agent 的价值来自独立任务并行，而不是 Agent 数量本身。显式触发、并发槽位、上下文派生和共享文件系统约束共同控制成本和冲突。

## 16. 容易产生的误读

### 16.1 “rollout 里出现”不等于“每轮完整重发”

日志记录的是事件和恢复历史。普通后续轮没有重复前三组 developer 消息，不代表这些规则失效；更可能是会话级上下文仍在，或日志只记录增量。

### 16.2 `developer` 消息不应全部叫作 `system` 消息

广义上它们都属于“系统提供的提示词”，但角色上应区分 `base_instructions`、`developer`、环境消息、turn metadata 和用户消息。混称会掩盖覆盖关系和装配时机。

### 16.3 Skill 列表不等于 Skill 正文已进入上下文

初始目录只提供触发描述和来源。只有选中后才要求完整读取 `SKILL.md`，再按需读取下游资源。

### 16.4 工具被提到不等于工具可用

文字可以规定“若存在则使用”，实际调用仍取决于本轮 schema。`request_user_input` 的规则正是显式例子。

### 16.5 多 Agent 能力存在不等于可以自动启动

团队协议声明能力，后续覆盖声明当前策略。样本的有效策略是 `explicitRequestOnly`。

### 16.6 “固定”不等于永久不变

两份日志只能证明相应文本在两个样本中相同。客户端升级、模型升级、个性切换和策略发布都可能替换固定模板。

### 16.7 `danger-full-access` 不等于无限授权

它只描述 sandbox 能力。用户请求范围、破坏性操作规则和最小授权原则仍然有效。

## 17. 最终归类

如果必须压缩成“所有用户相同”和“按需拼装”两类，可使用以下结论。

### 所有用户相同的部分

这里特指同一 Codex 版本中不随普通用户设置变化的**规则骨架**：

- Agent 以完成用户目标为导向；
- 按请求类型控制副作用和授权范围；
- 尊重工作区已有修改，避免破坏性操作；
- 工具调用前后保持可见、真实、可验证；
- 区分阶段性 commentary 和自包含 final；
- 使用真实 tool schema，不伪造能力或成功状态；
- Skills 采用触发、完整读取、最小集合和渐进披露协议；
- 长任务支持中断、恢复和上下文压缩后的连续执行。

### 按需拼装的部分

- personality 对应的个性与表达模板；
- Desktop、CLI 等宿主应用模块；
- sandbox、approval、network 和 permission profile；
- Default、Plan 等 collaboration mode；
- plugin 协议是否启用，以及插件提供的能力；
- 当前 Skill 目录、Skill 描述版本和本地缓存路径；
- 工具 schema 与 MCP / app 能力；
- 多 Agent 协议版本、激活策略、角色和并发槽位；
- cwd、shell、日期、时区、workspace roots；
- model、reasoning effort、feature flags 和 turn ID；
- 对话历史、工具结果和 compaction 摘要。

最准确的一句话总结是：**Codex 的“系统提示词”由一个相对稳定的 Agent 行为内核，加上一组由产品界面、用户设置、插件能力和每轮环境状态驱动的条件模块，再加上动态工具 schema 与会话历史共同组成。**
